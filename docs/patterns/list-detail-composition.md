# List–detail composition · Vanya Arc / UI

**Нормативный паттерн.** Для каталогов, настроек и рабочих интерфейсов, где человек выбирает объект слева и читает/редактирует его справа. Это **не** дизайн отдельного продукта и не лицензия на копирование стороннего UI. [Исследование](../research/list-detail-composition-2026-11-22.md) · [Правила скролла](../research/workspace-scroll-composition-2026-11-21.md) · [Типографика](typography.md) · [Браузерная навигация](browser-navigation.md).

## Основная задача композиции

**Выбор и содержание должны ощущаться одной поверхностью.** Композицию определяет информационная нагрузка, а не симметрия двух колонок.

1. **Навигация — самая узкая полезная колонка.** Начальный ориентир для desktop: 260–360 CSS px, с поправкой на доступную ширину, длинные названия и масштаб. Правая область получает остальное (обычно 60–75% рабочего пространства). Не делить 50/50 по инерции, когда справа длинные инструкции.
2. **Один главный заголовок страницы и один заголовок выбранного объекта.** Не ставить перед reader большой повторный hero с инструкцией «выберите слева». Глобальная навигация/хлебные крошки уже объясняют место. Если нужна краткая вводная, оставлять её в одну строку и не дублировать данные.
3. **Колонки визуально связаны.** Начала списка и reader выровнены по горизонтальному ритму; выбранный пункт имеет заметное, но тихое постоянное состояние (акцентная линия/поверхность и текст, а не один hover). Reader обновляется, не теряя список из виду.
4. **Внутри reader ширина отдана содержанию.** Длинный вопрос, название и инструкция занимают широкую текстовую колонку. Короткий тип, число, дата, статус — компактная подпись рядом. Параметр `max-content` для короткой метки полезнее второй текстовой колонки фиксированной ширины. При узком reader метка переносится под текст.
5. **Отступы показывают структуру.** Близкие элементы — компактно (4–8 px), строки одного раздела — примерно 8–12 px, разные разделы — примерно 16–24 px. Это **наши рабочие начальные значения**, не нормы Material/Carbon. Границы между разделами задают сильнее, чем повторяющиеся карточки и крупные пустые промежутки.
6. **Не уменьшать основной текст, чтобы влезло.** Для читательской части применять `ui-type-body` или `ui-type-compact` (14px минимум для длинного рабочего текста в текущей шкале). Метаданные могут быть мельче и моноширинными, но не превращать вопросы, описания и шаги в `10px caption`. Предел длины абзаца ~66ch; строки таблиц и `dl` имеют собственную геометрию.
7. **Выборочные подробности — в потоке документа.** Технический JSON, длинные caveats и альтернативные конфигурации можно свернуть нативным `details` с информативным `summary`. Главное решение/шаг/ссылка остаются видимыми. Не заменять право увидеть полную инструкцию попапом.
8. **Источники и следующие действия рядом с контекстом.** Ссылка на исходный документ — возле заголовка или конкретного шага; один набор метрик вместо копирования того же в обе колонки. Не выставлять в верх reader вспомогательную статусную ленту, если она не меняет действие пользователя.

## Плотная строка справочных данных

Для **read-only** перечня входных вопросов используйте семантический `dl`, но не превращайте его в форму. Тип источника — короткая метка, вопрос — главный текст.

```tsx
<dl className="reference-inputs">
  <div>
    <dt>Что человек хочет получить?</dt>
    <dd>Описание</dd>
  </div>
  <div>
    <dt>Есть ли подтверждённый пример?</dt>
    <dd>Источник</dd>
  </div>
</dl>
```

```css
.reference-inputs > div {
  display: grid;
  grid-template-columns: minmax(0, 1fr) max-content;
  gap: 16px;
  align-items: baseline;
}
@media (max-width: 600px) {
  .reference-inputs > div { grid-template-columns: minmax(0, 1fr); }
}
```

Это **не интерактивные поля**. Если действительно собираем ввод пользователя, применять формовые `label` и контролы с корректной программной связью; рекомендации W3C для форм не заменяют семантику `dl`.

## Владение прокруткой и адаптация

- Широкий desktop: sidebar-навигатор и reader — соседние зоны. Если обе имеют независимую прокрутку, используйте `WorkspaceSplit` с соседними `ScrollRegion`, имеющими явные размеры, подписи и доступ с клавиатуры. Если reader прокручивается самой страницей, допустим **один** ограниченный scroller списка; не смешивать случайно три вертикальных скролла.
- Навигационный скролл не должен обрезать первый активный пункт, особенно после восстановления/глубокой ссылки. При первой загрузке отобразить активный элемент целиком; при переключении не сбрасывать ручную прокрутку списка без необходимости.
- При смене выбранного объекта после глубокого скролла reader должен начинаться с заголовка **нового** документа. При `prefers-reduced-motion: reduce` — без плавного прыжка.
- При недостатке ширины: одна вертикальная прокрутка страницы; компактная горизонтальная лента выбора над reader либо один экран на действие с возвратом, в зависимости от длины списка. Не создавать вложенный длинный вертикальный список над длинной статьёй.
- Не привязывать мобильность только к `window.innerWidth`: учитывайте реальную ширину контента, соседнюю панель приложения и 200% zoom. Не допускать горизонтального скролла всего документа.

## Экран-рабочая область vs. длинная страница — обязательное решение

**Перед стилизацией выбери одного владельца вертикального скролла для каждого функционального контекста.** Если каталог одновременно содержит длинную навигацию и длинную инструкцию, обычная прокрутка `body` плюс `position:sticky` у списка — не эквивалент master–detail. Из-за этого заголовок выбранного документа уходит вместе со страницей, колонка списка ведёт себя независимо, а автоматический `scrollIntoView` прыгает всем приложением.

### Рекомендуемая структура для полноэкранного каталога

```text
App shell (100dvh, no outer vertical scroll)
├── Global sidebar (its own scroll when necessary)
└── Workspace (column, min-height: 0)
    ├── One compact global header with breadcrumbs and current reader context
    └── Main area (flex: 1, min-height: 0, no max-width centering)
        ├── List navigation (constrained height, own overflow-y: auto)
        └── Document reader (flex/grid sibling, own overflow-y: auto)
```

- **Не смешивай** `body`-прокрутку, sticky navigator, nested reader и `scrollIntoView` при каждой смене элемента. На desktop вертикальных scroll owners ровно два внутри рабочего пространства (список + reader); приложение и app header стоят неподвижно. Сайдбар может иметь собственный независимый scroll, если длинный.
- **`min-height:0` на каждом flex/grid предке reader** обязательно: `height:100dvh` на внешнем shell сам по себе не создаёт bounded scroll. `flex:1 1 0; overflow:hidden` у workspace, `overflow-y:auto` у конкретного reader/list. Нужны не только `sticky` и `max-height`.
- **Никакой центровки для рабочей области:** `max-width` и `margin-inline:auto` относятся к статьям/дашбордам, но не ко всему list–detail canvas. Reader заполняет остаток пространства, его абзацы могут иметь `max-width:66ch` отдельно. Внутренний отступ от app sidebar — небольшой (например 16–28 px), а не несколько вложенных `padding`.
- **Один глобальный header с текущим контекстом.** Хлебные крошки должны содержать реальную цепочку «Рабочая область → Каталог/Проект → Выбранный объект → Текущий раздел при прокрутке». Предки — настоящие ссылки; текущий объект и заголовок раздела видны, даже когда `h2/h3` reader прокручены. Не добавлять параллельный липкий заголовок над reader: это дублирует глобальную строку и отнимает высоту.
- **Переключение объекта:** меняй выбранный URL/state, сбрасывай *только* `reader.scrollTop=0` и текущий раздел; не двигай весь `window` и не сбрасывай навигационный scroller. Для восстановления глубокой ссылки прокрути *только список*, чтобы активная строка была видна.
- **Определение текущего раздела:** отслеживай `h3`/семантические секции относительно **scroll owner reader**, а не `window.scrollY`. При прокрутке до следующего раздела обновляй метку в единственной глобальной строке, не вставляя второй sticky layer.
- **Мобильный режим:** сохраняй фиксированный компактный global header, горизонтальную ленту выбора и **один вертикальный** reader. Уменьшай высоту навигации, а не высоту читательского текста; reader остаётся прокручиваемым в оставшемся `minmax(0,1fr)`.
- **Навигация:** объекты представлены ссылками `href` с поддержкой Ctrl/Cmd+Click и истории браузера. Если перехватывается обычный клик для SPA, обязательно `pushState` и `popstate`. `replaceState` не должен стирать историю выбора.

Это правило относится к **полноэкранному справочнику**. Для короткой статьи, обычной лендинговой страницы или страницы с единственным скроллом и без навигационного reader можно оставить обычную страницу; не вводить два scrollbar ради паттерна.

### Минимальная CSS-геометрия

```css
.workspace { height: 100dvh; display: flex; flex-direction: column; overflow: hidden; }
.workspace > header { flex: 0 0 auto; }
.workspace > main { flex: 1 1 0; min-height: 0; overflow: hidden; }
.list-detail { height: 100%; min-height: 0; display: grid; grid-template-columns: 320px minmax(0, 1fr); }
.list-detail > nav, .list-detail > article { min-height: 0; overflow-y: auto; overscroll-behavior-y: contain; }
@media (max-width: 900px) {
  .list-detail { grid-template-columns: 1fr; grid-template-rows: auto minmax(0, 1fr); }
  .list-detail > nav { overflow-x: auto; overflow-y: hidden; }
}
```

Компоненты `WorkspaceSplit` / `ScrollRegion` в библиотеке предоставляют геометрию и семантику; реальную привязку ко viewport, роутинг и текущую секцию обязан сделать потребляющий продукт. Отступы и breakpoint выбираются по доступной ширине *после* вычета сайдбара, не по ширине монитора в одиночку.

## Адресность и доступность

- Каждому выбранному разделу нужен прямой адрес с восстановлением при refresh и Back/Forward; в приложении используйте обычные ссылки или полноценный router. Визуальный selection не заменяет URL.
- Активный пункт доступно маркируется (`aria-current` для текущего места, либо подходящий selection pattern); focus-visible не прячем. Нельзя полагаться только на цвет.
- У reader есть семантический заголовок, порядок `h1→h2→h3`, читаемый текст и все источники в доступной области. Прокрутка не должна уводить фокус под sticky-элемент.
- Не путать детальный редактор и справочник: read-only `dl` не должен выглядеть как пустая форма.

## Перед принятием изменений

- [ ] 1600×900: справа достаточно места для длинных вопросов; нет «пустого второго столбца» внутри reader.
- [ ] 1280×800 и 1024×768: колонка reader не сплющивается после учёта app sidebar; когда тесно, layout адаптируется.
- [ ] 320×568 и 200% zoom: нет обрезанных вопросов, метки располагаются ниже текста, нет page-level горизонтального overflow.
- [ ] Первый, средний и последний элемент доступны без скрытого заголовка; активный визуально и семантически различим.
- [ ] Длинный список/короткая статья и длинная статья/короткий список не ломают владельцев прокрутки.
- [ ] Смена элемента при прокрученном reader показывает начало нового содержимого; список не теряет позицию.
- [ ] Light/dark, клавиатура, видимый фокус, длинные локализованные заголовки и reduced motion проверены.
- [ ] Источники кликабельны; скрытые JSON-подробности раскрываются клавиатурой, без второго модального слоя.
