# List–detail density and readable reference panels — research (2026-11-22)

**Статус:** исследование публичных UX-паттернов + редакционная интерпретация Vanya Arc / UI. Иллюстрации, пользовательские скриншоты, приватные данные и код внешних продуктов здесь не копируются. Правила внедрения: [list–detail composition](../patterns/list-detail-composition.md).

## Задача

В одном рабочем экране нужно быстро переключаться между 10+ разделами и целиком читать длинные инструкции со структурой «входные вопросы → варианты → решения → шаги → проверка → источники». На таком экране одновременно действуют две задачи: **найти объект** и **прочитать/сделать действие**. При неверном распределении ширины и отступов они начинают мешать друг другу.

## Что говорят первоисточники

| Первоисточник | Подтверждённый принцип | Применение в Vanya UI |
| --- | --- | --- |
| Google, *Build a list-detail layout* | List pane показывает выборку, detail pane — выбранное содержимое; широкий экран допускает две панели, узкий адаптирует представление | Выделять задачу списка и задачу reader, не держать две равные колонки просто ради симметрии |
| Microsoft Learn, *List/details pattern* | Паттерн строится на паре list/details и адаптируется к размеру экрана | Контекст выбора виден вместе с данными, пока для них есть ширина |
| IBM Carbon, *Structured list guidelines* | Иерархию внутри строк можно построить из связанных фрагментов разного веса; структурированный список предназначен для сканирования и выбора | Имя в строке ведущее, описание короткое, статус/счётчики вторичные; целая строка — hit target |
| W3C WAI, *Labeling Controls* | Для настоящих форм близость подписи и поля критична, расположение подписи сверху помогает при узкой ширине | Не сжимать длинный вопрос в узкую «label-колонку»; для справочного `dl` давать вопросу всю ширину, а короткую метку ставить сбоку/снизу |
| Vanya UI, *Scroll ownership and composition* | У скролла должен быть понятный владелец; не создавать конкурирующие вертикальные прокрутки и повторные sticky-заголовки | Избегать вложенного scroller внутри reader, а на компактном экране оставлять один вертикальный поток |
| Vanya UI, *Typography* и *Browser navigation* | Текст читается по роли; значимые виды имеют URL и работают с Back/Forward | Компактность достигается структурой, не микрошрифтом; deep link открывает тот же выбранный объект |

Внешние материалы не задают единственную универсальную ширину sidebar, отступ между панелями или количество строк preview. Числа ниже — **собственные решения Vanya UI**, подлежащие проверке на разных интерфейсах.

## Типовые ошибки и решение

**1. Панели равной ширины, задачи неравной сложности.** Если список состоит из названия и краткой подписи, но в reader живёт несколько сотен слов, деление 50/50 оставляет список чрезмерно широким, а вопросы, инструкции и код — тесными. Учитываем содержание: nav 260–360px, остальная ширина reader. При недостатке общей ширины переключаемся на последовательную компоновку.

**2. Внутри узкого reader вторая колонка для большого текста.** Формально это «ровная таблица», но длинные вопросы занимают 4–5 строк, а колонка вида `url`/ `text` визуально пуста. Для read-only перечня — `minmax(0,1fr) max-content`. Короткий `kind` может быть чипом с понятным названием; при тесноте переносится вниз. Для настоящих форм используем корректные `label` + `input`, не имитируем их определениями.

**3. Вступительная зона повторяет действие и метаданные.** Повторяющиеся брови, заголовки, подсказки «выберите элемент», счётчики в обеих колонках и статусная полоска задерживают доступ к первому содержательному разделу. Сохраняем один короткий заголовок экрана, один заголовок объекта, первичную ссылку и начинаем структуру материала.

**4. Пробелы не группируют смысл.** Одинаковые большие расстояния между связанными вопросами, описанием и типом нарушают смысловую близость. Используем 4–8px внутри одной сущности, 8–12px для строк, 16–24px между разделами, тонкое разделение на границе смысловых частей; не добавляем рамку на каждое поле.

**5. Active не связывает выбор и reader.** Постоянное выделение выбранной строки должно быть видно даже без hover. Используем тихий фон + 2–3px акцентную линию, не только цвет текста; содержание справа соответствует тому же идентификатору и URL.

**6. Потери контекста при прокрутке.** Если список держит собственный scrollbar, он должен открываться на первом/выбранном элементе, а после выбора новой статьи reader должен показывать начало её заголовка. Прокручивать всю страницу при каждом клике необязательно; переход нужен, только когда заголовок уже вне видимости.

**7. «Компактность» через микрошрифт.** Для длинного текста сохраняем содержательную шкалу `ui-type-compact`/body; уменьшаем повторения, число уровней заголовков и внутренние технические блоки. Подробную JSON-конфигурацию можно хранить в раскрытии внутри страницы без отдельного modal.

## Предложенная композиция (решение Vanya UI)

```text
├─ Компактный app header: текущий раздел / навигация / системные действия
└─ Содержание
   ├─ Заголовок экрана · один ряд
   └─ list–detail
      ├─ Навигатор (260–360 px)
      │  ├─ Список + количество
      │  ├─ Выбранный элемент (акцент)
      │  └─ Компактные строки: имя / краткое описание / метрики
      └─ Reader (остаток рабочей ширины)
         ├─ Название / одно описание / источники
         ├─ Входные вопросы: широкий текст + короткая метка
         ├─ Варианты внедрения (технические детали раскрываются)
         ├─ Правила выбора, шаги, проверка
         └─ Первоисточники
```

Это не универсальный макет для каждой страницы. Если справа только один абзац, постоянная широкая панель избыточна — выбираем простой список/инспектор. Если справа полноценный редактор, нужен явный save/status и свои scroll owners.

## Проверяемые критерии

- Человек видит выбранный модуль и начало его содержательного раздела в первом экране, не после двух hero.
- Вопрос с 60–80 символами не превращается в искусственный столбец по 150px при доступной ширине reader больше 600px.
- При ширине рабочего пространства около 700px макет не сохраняет две тесные колонки; список становится компактной навигацией над reader или отдельным шагом.
- Выбранный пункт виден и keyboard-focusable; long article + short list и short article + long list прокручиваются ожидаемо.
- На 200% zoom, при длинных словах и `prefers-reduced-motion` интерфейс остаётся читаемым.
