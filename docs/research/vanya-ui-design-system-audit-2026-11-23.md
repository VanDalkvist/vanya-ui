# Vanya UI — research loop: design-system health audit

**Дата:** 2026-11-23  
**Срез исходников:** [VanDalkvist/vanya-ui @ 4083f39](https://github.com/VanDalkvist/vanya-ui/tree/4083f39490da6865e5ba867636885fd2bdc6d385).  
**Формат:** независимое source-based expert review с критическим оппонированием и проверкой первоисточников; **не** пользовательское исследование, **не** сертификация WCAG, **не** пиксельный/визуальный QA.  
**Зона:** библиотека, дизайн-язык, витрина, docs/agents, React APIs, дистрибуция и реальное повторное использование. Данные о других приватных проектах не включены.

## TL;DR

**8.2 / 10 — сила авторского дизайн-языка и композиционных правил.**  
**6.7 / 10 — усреднённая зрелость системы по восьми аспектам.**  
**5.3 / 10 — операционная готовность (API, a11y, релизы, измерение эффекта).**

Это **оценки одного критического разбора, не измерения пользователей**. Они не сопоставимы напрямую с официальными оценками Apple, Carbon, Radix или других систем. Сила Vanya UI — узнаваемое представление об интерфейсе: спокойные утилиты, выразительная, но не повсеместная волна, устойчивый контекст, собственный скролл у соседних рабочих областей, взаимодействие по смыслу, а не декоративные кнопки. Слабость — отсутствует столь же сильное подтверждение того, что эти решения устойчивы в браузере, доступности, поставке и разных продуктах.

**Тезис критика:** «Ты построил хорошую философию, библиотеку компонентов и руководство для агентов, но ещё не построил работающий механизм, который доказывает, что пользователь и продукт от этого выигрывают».

## 1. Метод и происхождение оценок

Система проверена в публичном исходном дереве, компонентных файлах и документах на одном SHA. Количество: 48 экспортируемых компонентов; 24 Vitest-файла / 103 пройденных теста и 18 Node-проверок по подтверждённому Cloudflare Build этого SHA; наличие portable CLI и авторской документации. Эти тесты **не равны** независимому browser/accessibility audit.

Метод A: **авторская восемь-критериальная шкала 0–10**, одинаковый вес; 0 — отсутствует, 5 — работает, но сильно ограничено, 8 — устойчиво и осознанно, 10 — доказано на масштабе и потребителях. Шкала **не** стандартизирована. Визуальная оценка основана на токенах, CSS, семантике и истории изменений; без нового снимка экрана её достоверность снижена.

Метод B: шесть независимых осей [zeroheight Design System Maturity Model](https://zeroheight.com/maturity/) (Foundations, Documentation, Governance, Adoption, Measurement, AI readiness), приблизительно сопоставленные с четырьмя уровнями. **Это не официальная 29-вопросная сертификация.**

Метод C: UX проблемы по [эвристикам Nielsen–Molich](https://www.nngroup.com/articles/ten-usability-heuristics/) с серьёзностью 0–4, ориентируясь на частоту, силу воздействия и повторяемость. [Смысл severity](https://www.nngroup.com/articles/how-to-rate-the-severity-of-usability-problems/). Ниже severity — одна экспертная оценка, не консенсус нескольких независимых оценщиков.

Метод D: benchmark отдельных проверяемых критериев к [Apple HIG](https://developer.apple.com/design/human-interface-guidelines/design-principles/), [W3C ARIA APG](https://www.w3.org/WAI/ARIA/apg/patterns/), [Atlassian](https://atlassian.design/contribution), [Storybook](https://storybook.js.org/docs/writing-tests/accessibility-testing) и [DTCG stable 2025.10](https://www.designtokens.org/faq/). **Не «мы лучше или хуже Apple на 2 балла», а соответствие конкретным механизмам.**

## 4. Что стоит похвалить — без авансов

**Редкий продуктовый вкус.** Ты не заменил UI на сборник shadcn/Radix копий: отдельное понимание, что такое контекст, иерархия, детали и право действий занимать экран. Решения в [working-surfaces](../composition/working-surfaces.md), [list-detail](../patterns/list-detail-composition.md), [interaction-states](../patterns/interaction-states.md) связаны с конкретными jobs, а не «красивыми эффектами».

**Архитектурная дисциплина выше многих личных библиотек.** [src/index.ts](../../src/index.ts) имеет типизированные exports; отдельный [brand package](https://github.com/VanDalkvist/vanya-arc-brand) и права на айдентику; запрет расходиться локальным палитрам; [portable pipeline](../patterns/ui-feature-pipeline.md), который можно запускать без GitHub Actions и привязки к хостингу.

**Живой демонстратор, а не только статическая картинка.** Сцены, SineWave, составные компоненты, hover/focus/press стенды, controlled actionState с настоящим выбором успеха/ошибки; раньше неудобный док «Клавиши» был убран, чтобы не перекрывать основной слайдер. Способность менять решение после фактического сбоя важнее верности своему первому макету.

**Документирование исследования.** Сохранённые research/critical loops и ссылки на первоисточники позволяют агенту проверять намерение. Это сильная основа для передачи между машинами и проектами.

## 5. Прожарка — проверяемые находки

### UX-01 [severity 3/4] — Вкладки, которые только называются вкладками

[SegmentedControl.tsx](../../src/components/SegmentedControl.tsx) по умолчанию использует semantics="tabs", role="tablist"/role="tab" и aria-selected, **но** не реализует roving tabindex, ArrowLeft/Right/Home/End и связь с tabpanel/aria-controls. Это не реализация [W3C APG Tabs Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/). Для фильтров уже есть корректнее названный semantics="filters", но tab-режим как публичный API создаёт ложное обещание доступности.

**Что проверять:** полный APG keyboard contract и панели, либо запретить/удалить псевдо-tabs и использовать только filters до появления настоящей Tabs abstraction. Не подменять ARIA-атрибуты фактом соответствия.

### UX-02 [severity 3/4] — Меню темы всё ещё не дотягивает до menu pattern

[ThemeToggle.tsx](../../src/components/ThemeToggle.tsx) хорошо поддерживает Escape, ArrowUp/Down и aria-checked. Но все кнопки с role=menuitemradio остаются в стандартном tab order (не заданы tabindex=-1/roving), а Tab/Shift+Tab не закрывают меню. Согласно [W3C APG Menu and Menubar](https://www.w3.org/WAI/ARIA/apg/patterns/menubar/) пункты menu — composite widget; Tab покидает его и закрывает меню. Наличие keyboard tests на стрелки не доказывает полный паттерн.

**Что проверять:** Tab, Shift+Tab, возврат фокуса, Escape, focus-out, screen reader и принудительные цвета; закрывать меню при выходе фокуса. Не заявлять WCAG-pass до live-проверки.

### UX-03 [severity 2/4] — Заголовок не указывает текущий раздел

[ShowcaseHeader.tsx](../../src/showcase/ShowcaseHeader.tsx) передаёт NavLinks 8 URL anchors **без** isActive. [NavLinks.tsx](../../src/components/NavLinks.tsx) умеет aria-current и выделение, но витрина их не подключает. Это локальная недоделка ориентации при скролле, не дефект каждой реализации компонента.

**Что проверять:** current section по scroll/URL с сохранением Back/Forward; не красить hovered как selected; не создавать ложный current при промежуточной прокрутке.

### QA-01 [риск 3/4] — Тесты доказывают JSX, но не реальный экран

В package.json есть Vitest/jsdom, 103 компонентных проверки и переносимые проверки агентов; **нет** Playwright/axe как обязательного уровня именно библиотеки, матрицы реальных браузеров/скриншотов и тестов перекрытия fixed UI в CI. Последний док справки прошёл тесты, а слайдер всё равно был закрыт. Это не гипотеза о возможном риске — уже наблюдавшийся класс отказа.

**Граница:** не требуется Storybook как религия. Достаточно 5–8 воспроизводимых browser-сценариев с проверкой light/dark, 320/390/1024/1440px, 200% zoom, keyboard, forced-colors, reduced motion, screenshots и отсутствие перекрытий. [Storybook](https://storybook.js.org/docs/writing-tests/accessibility-testing) — один из возможных способов, а не обязательная платформа.

### DIST-01 [риск 3/4] — Поставка библиотеки не соответствует зрелости кода

[package.json](../../package.json) указывает публичный export "." на **./src/index.ts** и отдельный src/tokens.css; main/types при этом говорят про dist. Это source-distribution для transpile-friendly React/Vite/Bun-проектов, **не готовый универсальный собранный npm package contract**. Тестов установки в нейтральном consumer с другим сборщиком не обнаружено. [Versioning](../versioning.md) честно требует tag v0.2.0, но на момент аудита публичные GitHub API **не возвращают тег v0.2.0 и Releases**. При этом после 0.2.0 в Unreleased накопились изменения поведения.

**Суть:** «у меня есть версия в package.json» ≠ «у меня воспроизводимый release artifact». Для внутренней SHA-pinned модели это приемлемый временный компромисс, но он должен быть признан и проверен минимум в двух реальных consumers.

### DX-01 [риск 2/4] — Библиотека может превратиться в «наши полезные штуки»

[Exports](../../src/index.ts) одновременно включают общие ActionButton/ActionLink/ScrollRegion, композиционные WorkspaceSplit/InspectDrawer и специфичные SineWave/HearthPulse/EnergyRadar/SpiderRadar. Это не ошибка сама по себе — продукты автора имеют право на общую эстетику, — но без **разделения core / composition / narrative / domain** следующий компонент легко окажется в shared package просто «на всякий случай».

**Дополнительная API-шероховатость:** [CraftCard](../../src/components/CraftCard.tsx) по-прежнему принимает isInteractive, но в реализации флаг намеренно игнорируется: интерактивность решает наличие onClick. Это плохая семантика prop API, пока флаг не deprecated/удалён по правилам версии.

### CONSISTENCY-01 [риск 2/4] — Система правил иногда опережает стили

Новый контракт нейтрального hover говорит о разграничении hover и selected, но [tokens.css](../../src/tokens.css) содержит старые локальные исключения: breadcrumbs:hover, MediaCard title:hover и clear search:hover всё ещё используют accent. Для media можно обосновать художественную роль, для обычного breadcrumb — сложнее. Здесь не нужен запрет на оранжевый цвет; нужен классификатор: **исключение с объяснением или рефакторинг к роли**.

### IMPACT-01 [риск 2/4] — Нельзя доказать, что система уменьшает работу

Публичный [Ferma package.json](https://github.com/VanDalkvist/ferma/blob/main/package.json) закрепляет @vanya/ui на SHA 46ee8a80…, то есть реальный consumer подтверждён. Но **нет** панели: сколько UI взято из пакета, где остаются локальные копии/override, какой потребитель отстаёт от текущей версии, сколько раз агент нарушил контракт, сколько минут ушло на апгрейд. [zeroheight 2026](https://report.zeroheight.com/2026) относит adoption и measurement к самостоятельным осям зрелости. Система может быть красиво устроена и при этом не снижать стоимость работы.

## 6. Совет критиков: пять оппонирующих перспектив (не пять независимых экспертов!)

**Apple/HIG-ориентированный дизайнер:** «Язык цветов и движения уже есть. Но приоритет — не тишина, а предсказуемость. Не надо ещё один красивый hover, пока непроверены keyboard/zoom/конфликт слоёв».

**Radix/accessibility-инженер:** «Роли tab и menuitemradio — это обязательства по взаимодействию. Полуреализованная ARIA иногда хуже простого нативного button/group. Либо соблюдайте [APG](https://www.w3.org/WAI/ARIA/apg/patterns/), либо не заявляйте роль».

**Дизайн-системный архитектор:** «48 экспортов ещё не экосистема. Определите уровни абстракции и критерий попадания в shared package. Core должен становиться меньше и надёжнее, а не расти с каждым продуктом».

**React-разработчик-потребитель:** «Почему версия 0.2.0 без тега, а exports ведут в TSX? Как проверить совместимость? Что изменится после апдейта SHA? Мне нужен release smoke, не ещё один README».

**Продуктовый критик:** «Сколько часов сэкономлено в Ferma? Какое решение теперь принимает агент без твоей помощи? Какой старый баг больше не возвращается? Если ответа нет, системная польза пока гипотеза».

**Ответ защитника системы:** для одного автора многие enterprise-ритуалы избыточны. Portable skill, строгая атрибуция, опубликованные правила и реальные примеры уже делают Vanya UI сильным internal product. Не пытайтесь получить все возможности Carbon/Apple; доказать работу собственных трёх ключевых jobs достаточно.

## 7. Решение critical loop: что делать, а что не делать

**Отвергнуть:** создать ещё 20 компонентов, делать Figma-кит ради бенчмарка, вводить автоматические GitHub Actions, срочно переходить на Radix везде, объявлять WCAG-pass по Vitest или делать UI «более как у Apple» путем копирования деталей.

**Принять три коротких, законченных цикла:**

| Шаг | Ограниченный scope | Definition of Done | Решение после |
| --- | --- | --- | --- |
| A — Interaction Truth | Только SegmentedControl tabs, ThemeToggle menu и 1 реальный пользовательский маршрут по витрине | Browser test + screen reader sanity + keyboard APG; скриншоты 2 темы × 3 widths, без перекрытия slider | Закрыть UX-01/02 или честно убрать недоделанные роли |
| B — Release Truth | Упаковка, source-export contract, package smoke и versioning | 2 neutral consumer install/build tests, зафиксированный SHA, changelog, verified tag; manual workflow, без CI cron | Либо доказать source-distribution и оформить как контракт, либо перейти на dist export |
| C — Adoption Truth | Только Ferma как проверяемый consumer | Статический импорт/override audit, успешный ручной апгрейд, записанный baseline покрытия и времени, список обходов | Решить, какой один компонент стоит извлечь/исправить, а какой **не** должен попадать в core |

Не менять всё сразу: успех цикла — не переписанный код, а **сокращение неопределённости до решения**.

## 8. Метрики для следующих двух итераций

Хранить минимальный JSON-срез рядом с аудитом:

- QA: число компонентов с APG keyboard test / число компонентов с composite ARIA role; число визуальных baseline-сценариев, найденные visual regressions.
- Release: tag matches tested SHA, результат consumer smoke, drift в коммитах от используемой SHA.
- Adoption: список **проверенных** consumers, количество использованных exports, доля локальных overrides, трудозатраты на upgrade, время до первого успешного agent check.
- Experience: для 3 типовых tasks — success rate и количество неясных действий на первом экране. Без пользовательских сессий записывать «NOT MEASURED», не выдавать экспертный балл за KPI.
